# PassBuddy 受控内测文档规划

> 状态：Ready for execution
> 目标：把当前 Hackathon Alpha-Demo 升级为可面向约 100 名真实高校用户的受控外部内测版本。
> 执行模板：`docs/Development-Workflow-and-Instruction-Template.md`

## 1. 文档边界

### 1.1 现有文档的角色

- `docs/00_project_plan.md` 至 `docs/16_pdf_technical_proposal_revision.md` 保留为 Hackathon Alpha-Demo 的历史基线。
- 现有 `docs/01_alpha_contract.md` 明确把账号、历史记录和生产级合规排除在外，不能继续作为真实用户内测的完整契约。
- `docs/04_api_contracts.md` 中已有的画像、出题、报告、TTS、STT 契约继续有效；新增账号、持久化、反馈和运营接口必须以增量方式扩展，不得静默改变既有字段语义。
- `docs/todo.md` 继续记录全项目状态；本轮的权威范围、契约和验收证据放在 `docs/internal-beta/`，避免继续把规则埋在超长 TODO 中。
- `docs/Development-Workflow-and-Instruction-Template.md` 是任务执行模板，不承担产品范围、共享数据模型或全局验收矩阵的职责。

### 1.2 新文档的优先级

当内测文档与旧 Hackathon 文档冲突时：

1. 本轮已批准的 `internal-beta` Contract；
2. 本轮 API/Data Contract；
3. 本轮 Acceptance Matrix；
4. 旧 Hackathon Contract；
5. TODO、历史验证记录和讨论稿。

任何冲突必须登记为 Change Request，不允许在单个开发 instruction 中自行拍板。

## 2. 推荐目标阶段

推荐目标为 **受控外部内测（Beta-Lite）**，不是完整公开 Beta：

- 用户来自邀请码控制的两所高校，总量约 100 人。
- 主闭环必须真实落库、可追踪、可恢复。
- 必须具备邮箱验证码登录、权限隔离、隐私授权、反馈、基础指标和异常监控。
- 允许运营后台简陋、删除请求人工执行、指标通过现成工具和简单管理页查看。
- 不要求学校 SSO、手机号/学号登录、复杂用户历史页、自动化数据仓库或完整客服工单系统。

2026-07-23 用户确认按推荐默认值继续；2026-07-24 因国内邮箱送达约束触发 D-02/D-03 变更控制，已先更新 Contract 与 instructions，再恢复执行。

## 5. 开发顺序与集成门禁

### Wave 0：决策与契约

- 完成 01–06。
- 不修改业务代码。
- 停止点：范围、source of truth、权限和数据保留规则获确认。

### Wave 1：身份与数据底座

- 执行 IB-01、IB-02。
- 局部集成：用户通过邮箱验证码登录后，只能读取自己的最小用户记录。
- 停止点：OTP、Session、邀请码、越权测试通过。

### Wave 2：主闭环持久化

- 执行 IB-03、IB-04。
- 局部集成：登录用户完成一次面试，刷新或重新登录后，服务端仍能查到完整训练记录；隐私同意有版本和时间证据。
- 停止点：核心数据事务、失败恢复、用户隔离和删除演练通过。

### Wave 3：反馈与可观测性

- 执行 IB-05、IB-06。
- 局部集成：报告反馈、闭环完成、接口错误和延迟能够进入运营查询或现成工具。
- 停止点：指标口径与数据库抽样一致，告警故障注入通过。

### Wave 4：灰度放量

- 执行 IB-07 和 `08_pilot_release_and_acceptance.md`。
- 先 10–20 人，再约 50 人，最后开放到约 100 人。
- 每一档放量前检查完成率、模型失败率、P95 响应时间、邮件 OTP 成功率和严重错误数量。

## 6. 已确认决策

2026-07-23 用户接受 D-01 至 D-10 的推荐默认值，并要求整套文档完成后再统一调整。后续若改变关键决策，按第 7 节执行交叉更新。

| ID | 决策 | 推荐默认值 | 不确认的影响 |
| --- | --- | --- | --- |
| D-01 | 目标阶段名称与质量门槛 | 受控外部内测 Beta-Lite | Contract 和验收深度不稳定 |
| D-02 | 认证/数据库/邮件方案与部署地域 | Next.js 自托管 Better Auth；腾讯云同地域 PostgreSQL；腾讯云 SES API 发信 | SDK、迁移、Session 和邮件送达无法冻结 |
| D-03 | 邮箱验证码规则 | 无密码 6 位数字验证码；30 分钟有效；60 秒重发；最多 3 次错误尝试；重发旋转旧码；安全 Cookie Session；QQ/163/学校域名实测 | 登录接口和异常语义无法冻结 |
| D-04 | 邀请码与邮箱限制 | 邀请码绑定学校；邀请码是准入主条件；学校邮箱域名仅做辅助校验 | 普通邮箱、校友邮箱和跨学校邀请码行为不明确 |
| D-05 | 训练数据保存范围 | 保存简历/JD 文本、画像、题目、转写文本和报告；不保存原始音频 | 数据模型、隐私协议和成本无法确定 |
| D-06 | 数据保留与删除 | 内测结束后保留 90 天；用户申请后由管理员人工删除并留痕 | 合规和运维流程无法验收 |
| D-07 | 反馈是否阻断报告 | 不阻断；报告展示后自愿反馈 | 若强制反馈，需要重新设计主闭环与退出行为 |
| D-08 | 管理员权限 | 单一 admin 角色；管理页不向普通用户暴露 | 看板和删除接口存在越权风险 |
| D-09 | 指标口径 | 服务端事件为完成率/错误率权威源，客户端事件仅补充页面漏斗 | 看板数字可能互相矛盾 |
| D-10 | 法务文案来源 | 产品/法务提供最终文本；开发只实现版本化展示、记录和更新提醒 | 开发不能自行承诺合规结论 |

## 7. 文档编写规则

- 共享 Contract 或 instruction 生成前必须通过技术栈适配核对，至少覆盖用户地域、可达性、真实邮箱/终端样本、配额成本、审核周期、故障退出和数据迁移。
- 先写共享 Contract 和 Matrix，再生成 instruction。
- 每份 `IB-*` instruction 使用 `Development-Workflow-and-Instruction-Template.md` 的完整版本。
- L1 instruction 至少包含 5 个失败/边界场景，L2 至少 3 个。
- Instruction 不复制整个全局 Contract，只引用并摘录与当前模块有关的硬约束。
- 每个数据库写接口必须定义认证、授权、校验、幂等或重复行为、失败原子性和审计字段。
- 每个管理接口必须定义 admin 权限和敏感字段最小化。
- 每个事件必须定义生产者、触发时机、去重规则和查询口径。
- 所有完成声明必须回填 `05_acceptance_matrix.md` 的证据，并在 `docs/todo.md` 登记摘要。
